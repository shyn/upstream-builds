# 实现前定义的失败场景与验收要求

1. 首次检查：没有成功记录时应构建；仅检查不能写成功状态。
2. 相同 SHA：已成功上传的 SHA 再次检查应跳过。
3. 新 SHA：上游更新时应构建，并固定 checkout 到检查时的完整 SHA。
4. 构建失败：不能运行后续发布任务，成功记录保持原值。
5. 产物缺失或上传失败：不能更新成功记录；下一次检查仍应构建。
6. 开启 Release 后发布失败：不能更新成功记录；下一次仍应构建。
7. 手动触发：默认仍比较 SHA；force=true 时允许重建相同 SHA。
8. 上游 404、鉴权失败、限流、服务错误：任务失败，不能误判成没有更新。
9. 状态读取 403/500、损坏的状态 JSON、错误的仓库/分支：任务失败，不能静默重建覆盖状态。
10. 状态更新失败：任务失败；下一次检查仍应重试。
11. 同一 SHA 重试发布：不能因已有 Release 导致永久失败；Release 标签按运行次数唯一。
12. 定时与手动重叠：同一 workflow 串行执行，不能取消正在构建的版本。
13. 旧任务重跑：检查后的状态若被更新，不能覆盖更新后的成功记录。
14. 上游仓库或分支改变：应使用独立成功记录，不能串用旧状态。
15. 构建进程：不注入发布令牌；上游 checkout 不持久保存凭据。

验证分为 workflow 静态检查、真实 GitHub 只读 SHA 检查、本地 HTTP API 场景验证，以及部署后 GitHub runner 验收。本地模拟不能替代真实 runner 打包、Actions Artifact 上传或 Release 发布验收。

## 用户要求统一多上游构建仓库后的新增验收（修改前定义）

16. 清单为空、重复 ID、无效仓库名、脚本路径越界或脚本不存在：计划阶段失败，不能启动错误构建。
17. 手动指定不存在的目标：明确失败，不能静默构建全部项目。
18. 多个上游：各自独立 SHA 与并发分组，一个项目失败不能取消其他项目。
19. 通用打包：打包脚本没有生成任何非空文件时失败，不能只上传元数据后误记成功。
20. 项目输出包含子目录：校验清单应保留相对路径，下载后能够复验。
21. 创建 GitHub 仓库：先确认账号与同名仓库情况，再创建；提交与实际 runner 验证分别记录。
22. 真实 GitHub 验收：成功构建并上传有效 .pkg、发布 Release 后记录 SHA；再次检查相同 SHA 应跳过；使用真实成功记录只读验证 force=true 时仍应请求构建，避免为同一代码重复完整编译。

## 首次真实运行发现的构建检查错误

23. `lipo -verify_arch` 的架构列表是变长参数，输入文件必须放在命令前面；错误顺序会在安装包已生成后仍导致检查失败。修复命令后用本机生成的 arm64 Mach-O 文件验证调用，再完整重跑 GitHub runner 流程。
